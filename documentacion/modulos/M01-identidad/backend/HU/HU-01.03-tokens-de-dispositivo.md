## Especificación

**1. Rutas web** (grupo `web`, `auth`, Gate `emitir-tokens`). Sustituyen a las antiguas `/api/v1/identidad/tokens/...`, que usaban sesión y contradecían la regla de que las escrituras en la API exigen token:

| Método | Ruta | Acción | Cuerpo (`EmitirTokenRequest`) |
|---|---|---|---|
| `GET` | `/admin/tokens` | Lista los tokens y los dispositivos | — |
| `POST` | `/admin/tokens` | Emite un token de dispositivo. **Solo en la nave** (`SoloEnNodo:nave`): los dispositivos envían sus datos a la nave. En la Tierra, `dispositivos` llega vacío | `dispositivo_id` (obligatorio, UUID de un dispositivo existente según `ConsultaDispositivos::porId()`), `reemplazar` (booleano, opcional) |
| `DELETE` | `/admin/tokens/{id}` | Revoca un token | — |

**2. Emitir** (`Application/EmitirTokenDispositivo.php`):

| Caso | Resultado |
|---|---|
| El dispositivo es de tipo `tableta` (solo inventario) | `TabletaSinToken` (`IDENTIDAD_TABLETA_SIN_TOKEN`), error en `dispositivo_id`: "Las tabletas no usan token de dispositivo: el astronauta usa el de la PWA." |
| El dispositivo ya tiene un token y `reemplazar` no es `true` | `DispositivoConToken` (`IDENTIDAD_DISPOSITIVO_CON_TOKEN`), error en `dispositivo_id`: "Este dispositivo ya tiene un token vigente. Confirme si quiere reemplazarlo." |
| Caso normal (o `reemplazar = true`) | En una transacción: borra el token anterior del dispositivo (si lo hay) y crea `createToken('dispositivo:<identificador>', ['lecturas:escribir'])`, sin caducidad |

La respuesta redirige a `/admin/tokens` con `tokenNuevo` en el *flash* (texto plano, **una sola vez**). El controlador de `GET /admin/tokens` lo pasa como *prop* `tokenNuevo` y **nunca** se escribe en los *logs*.

**3. Revocar** (`Application/RevocarToken.php`):
- Borra la fila de `personal_access_tokens`.
- **Los tokens de nodo solo los revoca el rol `admin`** (*Policy* `TokenPolicy::revocar`). Un ingeniero recibe `403`, porque revocarlo corta la sincronización.
- Los tokens de dispositivo y de la PWA los revocan el ingeniero y el admin.

**4. Middleware `TokenDeTipo:<tipo>`** (`dispositivo`, `pwa` o `nodo`). Se usa en **todas** las rutas `POST` de `/api/v1/...`, siempre junto a `auth:sanctum`:

| # | Comprobación | Si falla |
|:---:|---|---|
| 1 | `$request->user()?->currentAccessToken()` es un `Laravel\Sanctum\PersonalAccessToken`. Con la sesión del navegador, Sanctum devuelve un `TransientToken` y `tokenCan()` responde `true` a todo, por eso se comprueba la clase | `401` `IDENTIDAD_TOKEN_REQUERIDO`: "Las escrituras en la API requieren un token." |
| 2 | El token tiene la habilidad del tipo pedido (`lecturas:escribir`, `registros:escribir` o `sync:escribir`) y el dueño es de la clase correcta (`Dispositivo`; `User` con rol `astronauta` o `cmo`; `User` con rol `sistema`) | `403` `IDENTIDAD_TOKEN_NO_PERMITIDO`: "Este token no permite esta operación." |
| 3 | Si el dueño es un usuario, sigue `activo` | `401` `IDENTIDAD_USUARIO_DESACTIVADO`: "Usuario desactivado." |

Las tres respuestas usan el [sobre de error](../../../00-arquitectura/ARCHITECTURE.md#12-estándar-json) (`success: false`, `code`, `message`, `data: null`, `errors: {}`, `meta`).

Se permite más de un tipo en la misma ruta: `TokenDeTipo:pwa,dispositivo`.

**5. Token de nodo** (`php artisan identidad:token-nodo {remoto}`, con `remoto` igual a `nave` o `tierra`):
- Se ejecuta en el nodo que **recibe**. Ejemplo: en la Tierra, `identidad:token-nodo nave` emite el token del usuario `nodo-nave`.
- Si `remoto` es igual a `APP_NODO`, falla con "El token se emite para el otro nodo".
- Borra el token anterior de ese usuario y crea uno nuevo con `createToken('nodo:nodo-nave', ['sync:escribir'])`, sin caducidad.
- Imprime el token **una vez** y el aviso "Copie este valor en NODO_REMOTO_TOKEN del .env del nodo nave. La sincronización falla hasta que lo haga."
- Auditoría: `crear`, `recurso_tipo = tokens`, `actor = consola`.

**6. Auditoría** (HU-01.04 ya existe en este sprint): emitir → `crear`; revocar → `anular`. En los dos casos, `recurso_tipo = tokens` y `recurso_id` = `id` del token.

## Criterios de aceptación

- **Dado** el ingeniero biomédico, **cuando** emite un token para `astroskin-T2`, **entonces** ve el texto plano una vez y, al recargar la página, ya no aparece.
- **Dado** el token de `astroskin-T2`, **cuando** el simulador hace `POST /api/v1/ingesta/lotes` con `Authorization: Bearer <token>`, **entonces** no recibe `401` ni `403` por M01 (el resultado del lote lo decide M03).
- **Dado** que el token fue revocado, **cuando** el simulador lo vuelve a usar, **entonces** recibe `401`.
- **Dado** un astronauta con sesión de navegador y sin token, **cuando** hace `POST /api/v1/ingesta/lotes`, **entonces** recibe `401` con "Las escrituras en la API requieren un token.".
- **Dado** un token de dispositivo, **cuando** llama a una ruta con `TokenDeTipo:nodo`, **entonces** recibe `403`.
- **Dado** `astroskin-T2` con token, **cuando** se emite otro sin `reemplazar`, **entonces** se rechaza; **y con** `reemplazar = true`, **entonces** el anterior deja de funcionar y el nuevo funciona.
- **Dado** el ingeniero biomédico, **cuando** intenta revocar el token de `nodo-nave`, **entonces** recibe `403`; el admin sí puede revocarlo.
- **Dado** la Tierra, **cuando** ejecuto `php artisan identidad:token-nodo tierra`, **entonces** falla con "El token se emite para el otro nodo".
