## Especificación

**1. `POST /api/v1/ingesta/lotes`.** El cuerpo es el de la [ficha §1](../README.md#1-api-rest).

**2. Validación del esquema** (`LoteRequest`) → `422` y no se guarda nada:

| Campo | Regla |
|---|---|
| `lote_id` | Obligatorio, UUID |
| `dispositivo_id` | Obligatorio, texto ≤ 60 |
| `tripulante_id` · `ubicacion` | **Exactamente uno** de los dos con valor. Ambos o ninguno → `lote_mixto` |
| `modo` | `vivo` o `historico` |
| `enviado_en` | Obligatorio, fecha ISO 8601 |
| `bateria_pct` | Opcional, entero 0–100 |
| `lecturas` | Array de 1 a **5.000** elementos |
| `lecturas.*.id` | UUID; **sin repetidos dentro del lote** (`ids_repetidos`) |
| `lecturas.*.codigo` · `unidad` | Texto ≤ 20 |
| `lecturas.*.valor` | Numérico |
| `lecturas.*.medido_en` | Fecha ISO 8601 |
| `lecturas.*.calidad` | Opcional, número entre 0 y 1 |
| `lecturas.*.contexto` | Lote personal: obligatorio, `reposo`, `ejercicio` o `sueno` (`contexto_requerido`). Lote ambiental: debe ser `null` (`contexto_no_permitido`) |

**3. Orden de procesamiento** (`Application/ProcesarLote.php`). Se adelanta la autorización respecto de la ficha anterior, para que un `lote_id` ajeno no devuelva el resumen de otro dispositivo:

| # | Paso | Si falla |
|:---:|---|---|
| 1 | Token de dispositivo (`TokenDeTipo:dispositivo`) | `401` / `403` (M01) |
| 2 | Esquema (`LoteRequest`) | `422` |
| 3 | Existencia, con los contratos de M02: el `dispositivo_id` existe (`dispositivo_desconocido`); no es de tipo `tableta` ni `simulador` (`dispositivo_no_admitido`); el tripulante (por código) o el módulo (por código) existe en la misión activa (`tripulante_desconocido`, `ubicacion_desconocida`) | `422` |
| 4 | **Autorización.** Si el dueño del token no es el simulador, el dispositivo nombrado debe ser el dueño del token. En todos los casos (también con el simulador), el dispositivo nombrado debe estar asignado **a ese** tripulante o módulo | `403` `{"message": "El dispositivo no puede escribir para ese tripulante o ubicación."}` |
| 5 | **Idempotencia del lote** (detalle abajo) | `200` con el resumen original |
| 6 | Cada lectura: duplicados y validaciones de HU-03.02 | Se cuenta; el lote sigue |
| 7 | Inserción en bloques de 1.000 con `insertOrIgnore`, en la misma transacción | — |
| 8 | `ConsultaDispositivos::marcarContacto(<nombrado>, bateria_pct)` y, si el token es del simulador, también `marcarContacto('simulador', null)` | — |
| 9 | Confirmar y publicar `LoteIngerido` (`ShouldDispatchAfterCommit`), **solo si `n_guardadas > 0`** | — |

**4. Origen de las lecturas.** `origen = simulador` si el **dueño del token** es un dispositivo de tipo `simulador`; si no, `sensor`. La ficha anterior lo decidía con el dispositivo nombrado, y entonces los datos simulados enviados en nombre de `astroskin-T2` quedaban marcados como `sensor`.

**5. Idempotencia y concurrencia**

- Todo el procesamiento va en `Transaccion::ejecutar(fn () => …, intentos: 3)` ([ARCHITECTURE §22](../../../00-arquitectura/ARCHITECTURE.md#22-transacciones)). El 3 son los reintentos ante un *deadlock*, posibles cuando dos lotes distintos comparten lecturas.
- Lo **primero** dentro de la transacción es `INSERT` de la fila de `lotes_ingesta` con contadores a 0.
- Si ese `INSERT` lanza `Illuminate\Database\UniqueConstraintViolationException` (el lote ya existía, o lo está procesando otra conexión, que se queda esperando el bloqueo hasta que la primera confirme), se sale de la transacción, se lee la fila **fuera** de ella y se responde `200` con su resumen. **Nunca** `500`.
- Al final de la transacción se actualizan los contadores, `medido_desde`, `medido_hasta` y `detalle_rechazos` de esa misma fila.

**6. Duplicados de lectura.** Antes de insertar, `SELECT id FROM observaciones WHERE id IN (...)` en bloques de 1.000. Esas lecturas cuentan como `duplicadas` y no se validan más. Si después `insertOrIgnore` inserta menos filas de las previstas (carrera con otro lote), la diferencia se suma a `duplicadas` y se resta de `guardadas`.

**7. Respuestas.**

| Código | Cuerpo |
|---|---|
| `201` | `{ "lote_id", "guardadas", "artefactos", "rechazadas", "duplicadas" }` (`guardadas` incluye los artefactos) |
| `200` | El mismo cuerpo, leído de `lotes_ingesta` |

**8. Evento `LoteIngerido`** (payload del [índice de módulos §5](../../../README.md#5-eventos-de-dominio)): `lote_id`, `dispositivo_id`, `tripulante_id` o `null`, `ubicacion` (id del módulo) o `null`, `codigos[]` (distintos, de las lecturas guardadas), `desde` y `hasta` (`medido_desde` y `medido_hasta`), `n_guardadas`, `n_artefactos` y `modo`.

**9. Colas** ([ficha §3.2](../README.md#32-rendimiento-en-cpanel)). Cada *listener* de `LoteIngerido` (en M04, M09, M12 y M15) implementa `ShouldQueue` y `viaQueue(LoteIngerido $e): string`, que devuelve `'historico'` si `$e->modo === 'historico'` y `'default'` si no. El *scheduler* ejecuta cada minuto `queue:work --queue=default,historico --stop-when-empty --max-time=55` con `->withoutOverlapping()`. Esta regla se documenta aquí y la cumple cada módulo en su *listener*.

**10. Consulta de periodo para el simulador** (sustituye el uso de `estado-sensores` que hacía el simulador, que con su token no funcionaba):

| | |
|---|---|
| Ruta | `GET /api/v1/ingesta/periodo?desde=<ISO>&hasta=<ISO>` |
| Autenticación | `auth:sanctum` + `TokenDeTipo:dispositivo`, y el dueño del token debe ser de tipo `simulador` (si no, `403`) |
| Respuesta | `200` `{ "hay_lecturas": bool, "lotes": int }`: lotes con `medido_desde <= hasta` y `medido_hasta >= desde` |

**11. Prueba de carga** (se mueve aquí desde el Sprint 0, porque el endpoint no existe antes).

- Comando `php artisan ingesta:prueba-carga --url=<nodo> --token=<token del simulador> --lotes=200 --lecturas=5000`. Genera lotes válidos con lecturas sintéticas de FC de T1 (`astroskin-T1`), con UUID v7 y `modo = historico`. Los envía por HTTP de uno en uno y muestra el tiempo medio, el máximo y el total de recepción.
- Comando `php artisan ingesta:estado-cola`: muestra cuántos trabajos quedan en `jobs` por cola. Se ejecuta varias veces en cPanel para medir el tiempo de vaciado.
- **Decisión** (se anota en la revisión del Sprint 1): si el relleno completo (~14.000 lotes) tardaría más de 1 hora en procesarse en cPanel, el relleno de la demo se hace en local y se importa la base.

## Parte B (Sprint 4, dentro de HU-15.02) · Importación en el nodo Tierra

- **El paquete `detalle` de M15 debe incluir las filas de `lotes_ingesta`** de las lecturas que lleva. `observaciones.lote_id` tiene clave foránea, así que importar lecturas sin su lote falla.
- Contrato: `ImportacionLotes::importar(array $lotes, array $observaciones): void`. En una transacción: `insertOrIgnore` de los lotes y después de las observaciones, **con sus mismos `id`, `es_artefacto` y `origen`**. No repite la autorización ni las validaciones (la nave ya validó), así que funciona aunque el dispositivo aún no exista en la Tierra.
- Publica `LoteIngerido` por cada lote importado con lecturas nuevas. Esos eventos llevan `importado = true`: M12 y M15 los ignoran, y M04 recalcula sus agregados.

## Criterios de aceptación

- **Dado** el token de `astroskin-T2` y un lote válido de 60 lecturas de T2, **cuando** se envía, **entonces** responde `201` con `guardadas = 60`; **y al** reenviarlo, `200` con el mismo cuerpo y ninguna fila nueva.
- **Dado** dos envíos simultáneos del mismo lote (dos procesos en la prueba), **cuando** terminan, **entonces** uno responde `201` y el otro `200`, nunca `500`.
- **Dado** una lectura ya guardada que vuelve en otro lote, **cuando** se procesa, **entonces** cuenta como `duplicada`.
- **Dado** un lote con `tripulante_id` y `ubicacion` a la vez, **cuando** se envía, **entonces** responde `422` con `lote_mixto`.
- **Dado** un lote con dos lecturas con el mismo `id`, **cuando** se envía, **entonces** responde `422` con `ids_repetidos`.
- **Dado** 5.001 lecturas, **cuando** se envía, **entonces** responde `422`.
- **Dado** un lote para `T9`, **cuando** se envía, **entonces** responde `422` con `tripulante_desconocido`.
- **Dado** el token de `astroskin-T2`, **cuando** envía un lote de T3 o uno con `dispositivo_id = cgm-T2`, **entonces** responde `403`.
- **Dado** el token del simulador, **cuando** envía un lote de `cgm-T3` para T3, **entonces** responde `201`, las lecturas tienen `origen = simulador` y `cgm-T3` y `simulador` actualizan su último contacto.
- **Dado** el token del simulador, **cuando** envía un lote de `cgm-T3` para T2, **entonces** responde `403` (no está asignado a T2).
- **Dado** una sesión de navegador sin token, **cuando** envía un lote, **entonces** responde `401`.
- **Dado** un lote con `bateria_pct = 40`, **cuando** se procesa, **entonces** el dispositivo queda con 40 %.
- **Dado** un lote cuyas lecturas son todas rechazadas, **cuando** se procesa, **entonces** responde `201` con `guardadas = 0` y **no** se publica `LoteIngerido`.
- **Dado** un lote `historico`, **cuando** se publica `LoteIngerido`, **entonces** sus *listeners* van a la cola `historico`.
- **Dado** lotes cargados del 1 al 30 de octubre, **cuando** el simulador consulta `/periodo` del 10 al 12, **entonces** recibe `hay_lecturas = true`; **y con** el token de `astroskin-T2`, `403`.
- **Dado** el cierre del Sprint 1, **cuando** se ejecuta la prueba de carga en el nodo nave de cPanel, **entonces** los tiempos y la decisión quedan anotados.
- **(Parte B) Dado** un paquete `detalle` con 60 lotes y sus lecturas, **cuando** se importa dos veces en la Tierra (sin que existan los dispositivos), **entonces** las lecturas se guardan una vez con su `origen` y su `es_artefacto`.
